# change-proposal

Claude Code 스킬. 사용자가 건넨 작업을 **착수 전에** 소스에서 확인해 근거와 함께 보고하고 승인을 받는다. 코드는 승인 뒤에 고친다.

일회성 리뷰 도구가 아니라 **평소 작업 흐름**용이다. 작업을 던지면 바로 편집이 시작되는 대신, "지금 코드는 이렇고 / 그 지적은 맞고 틀리고 / 이렇게 바꾸겠습니다"가 먼저 온다.

## 왜

건네받은 작업에는 보통 두 종류가 섞여 있다.

- 실제로 고쳐야 할 것 ("이 툴팁 문구가 이상하다")
- **틀린 전제** ("이 기능 이제 안 쓰는 거 아닌가?" — 쓰고 있다)

바로 착수하면 두 번째를 그대로 따라가 멀쩡한 걸 지운다. 이 스킬은 각 작업을 `file:line` 으로 대조한 뒤에야 답하게 한다.

## 어기지 않는 규칙 셋

1. **사용자의 표현과 구획을 그대로 쓴다** — 번호를 매겼으면 그 번호로, 문장으로 말했으면 그 문장으로. `SP1` `Task 2` 같은 앵커를 새로 만들지 않는다.
2. **모든 주장에 `file:line`** — 확인 안 한 문장을 확인한 문장과 섞지 않는다.
3. **전제가 틀렸으면 정정하고 실제 질문에 답한다** — 선택지 메뉴는 답이 아니라 회피다.

나머지(작업당 골격, 분량, 순서, 묶기)는 전부 **재량**이다. SKILL.md 가 기본값을 주고 어디서 벗어나도 되는지를 명시한다 — 규격화가 목적이 아니다.

## 언제 안 붙나

오타·값 하나 같은 기계적 편집, "그냥 해" 라고 한 경우, 아직 무엇을 만들지 안 정한 발산 단계. 분량은 작업의 무게를 따라가므로 작은 작업엔 짧은 보고가 붙는다.

## 산출물

대화 본문에 인라인 보고서 1개. 파일로 빼지 않는다.

```
작업별: 현재(코드 인용) → 사실 확인 → 수정안 → (갈림길일 때만) 선택지 표 + 권장
끝:     실행 계획(순서·커밋 경계·검증) + 승인 필요한 결정
```

## 트리거

`/change-proposal`, "고치기 전에 검토해서 제안해줘", "각 건 어떻게 할지 먼저 보고", "이거 맞는지 확인하고 방안 제시". 작업 요청에 자동으로 붙기도 한다.

## 인접 스킬과의 구분

| | 언제 |
|---|---|
| `superpowers:brainstorming` | 아직 무엇을 만들지 안 정했다. 발산부터 한다 |
| `superpowers:writing-plans` | 무엇을 할지 합의됐다. 실행 계획 **문서**를 쓴다 |
| **change-proposal** | 작업을 건네받았다. **그 전제가 사실인지부터** 확인해 답하고 승인받는다 |

## 설치

```sh
cp -r Skills/change-proposal ~/.claude/skills/
```

`~/.claude/skills/change-proposal/` 에서 자동 인식된다. 실행 파일 없음 — SKILL.md 뿐이다.
