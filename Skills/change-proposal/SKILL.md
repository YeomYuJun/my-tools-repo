description: Use before acting on work the user hands over - a request, a few asks bundled together, a list of fixes, numbered or not - whenever it is worth confirming what the code actually does before changing it. Checks each ask against the source, corrects premises that do not hold (cited by file:line), says what would change, and closes with an execution order plus only the decisions that genuinely need the user. One inline report, then wait for approval. Skip it for trivial mechanical edits, for open-ended ideation where nothing has been proposed yet (brainstorm instead), and for turning already-agreed work into a plan document (plan instead).

## 무엇을 하는 스킬인가

사용자가 작업을 건넸다. **착수 전에** 각 작업을 소스에서 확인하고, 확인한 것을 근거와 함께 돌려주고, 승인을 받는다. 코드는 승인 뒤에 고친다.

가치는 양식이 아니라 **검증**에 있다. 사용자가 말한 걸 말만 바꿔 되풀이하면 이 스킬은 아무것도 한 게 없다.

## 언제 쓰고, 언제 건너뛰나

**쓴다** — 사용자가 건넨 작업이 코드를 바꾸고, 그 작업이 선 사실 확인의 값어치가 있을 때. 여러 건이 묶여 오면 거의 항상 여기 해당한다. "이거 이제 안 쓰는 거 아닌가?", "이 부분 좀 이상한데" 같은 **의문형 요청은 특히** — 전제부터 확인해야 하는 신호다.

**건너뛴다** — 오타 수정, 값 하나 바꾸기처럼 확인할 전제가 없는 기계적 편집. 사용자가 "그냥 해" 라고 명시한 경우. 아직 무엇을 만들지 정하지 않은 발산 단계(그건 brainstorming).

애매하면 짧게 쓴다. 보고서 분량은 작업의 무게를 따라간다.

## 어기지 말 것 — 셋

**1. 사용자의 표현과 구획을 그대로 쓴다.**
사용자가 번호를 매겼으면 그 번호가 끝까지 유효하다. 번호 없이 문장으로 세 가지를 말했으면 그 세 가지를 그 표현대로 세운다. `SP1` `Task 2` `Phase A` 같은 앵커를 새로 만들지 않는다. 사용자는 자기가 한 말과 대조하며 읽는다 — 이름을 갈아치우면 그 대조가 끊긴다. 묶어서 처리해야 하면 "3과 1을 함께" 라고 쓰지 새 이름을 만들지 않는다.

**2. 모든 주장에 `file:line` 을 단다.**
"이 함수는 X 합니다"가 아니라 "[foo.ts:210](src/foo.ts#L210) 에서 X 합니다". 확인하지 않고 쓴 문장이 확인한 문장과 섞이면 안 된다. 근거를 못 찾았으면 못 찾았다고 쓴다 — 추측을 사실처럼 적는 것이 이 보고서를 망치는 유일한 방법이다.

**3. 전제가 틀렸으면 정정하고, 실제로 물은 질문에 답한다.**
"이거 이제 안 쓰는 거 아닌가?" 는 선택지를 달라는 게 아니라 **묻는 것**이다. 코드가 아니라고 말하면 "아니오, 근거는 여기" 라고 답한다. 사용자 말에 맞춰 선택지 메뉴를 차리는 건 답이 아니라 회피다. 반대로 사용자가 맞으면 짧게 맞다고 하고 넘어간다.

## 작업당 기본 골격

고정 서식이 아니라 **기본값**이다. 작업마다 필요한 만큼만 쓴다.

- **현재** — 지금 코드가 무엇을 하는지. 짧은 인용 + `file:line`.
- **사실 확인** — 사용자가 짚은 것이 맞는지, 원인이 무엇인지. 전제 정정이 있으면 여기.
- **수정안** — 무엇을 어떻게 바꿀지. 문구 변경이면 before/after 를 그대로 보인다.
- **선택지** — 진짜 갈림길일 때만. 표로, 각 안의 대가를 적고, 권장안을 표시한다.

한 줄이면 되는 작업은 한 줄로 끝낸다. 갈림길이 없으면 선택지 절을 넣지 않는다. 골격을 채우려고 없는 내용을 만들지 않는다.

## 끝맺음

- **실행 계획** — 순서(의존이 있으면 이유를 한 줄로), 커밋 경계, 검증 방법.
- **승인 필요한 결정** — 진짜 갈림길만. 기본값이 뻔하면 그냥 정하고 본문에 적는다. 각 결정에 권장안을 표시한다.

결정이 없으면 "결정 없음, 승인만 주시면 착수합니다" 로 끝내도 된다. 승인 항목을 억지로 만들지 않는다.

## 재량 — 여기서는 판단해서 벗어나라

- **분량은 작업의 무게에 맞춘다.** 문구 하나 고치는 데 표를 그리지 않고, 아키텍처가 걸린 작업을 세 줄로 접지 않는다.
- **묶어도 된다.** 같은 원인에서 나온 작업들은 함께 다루는 게 더 읽힌다. 대신 사용자가 말한 항목을 전부 언급해서 빠진 게 없음을 보인다.
- **순서를 바꿔도 된다.** 의존이 있으면 그 순서로 재배열하고 이유를 적는다.
- **말 안 한 걸 발견하면 말한다.** 조사하다 나온 별건은 끝에 짧게 덧붙이고, 이번 범위에 넣을지는 사용자가 정하게 한다. 몰래 끼워 넣지 않는다.
- **"전부 검토" 류는 숫자로 바꾼다.** 열린 쓸기는 승인할 수 없다. 분류 + 개수로 제시해서 사용자가 범위를 승인하게 한다(예: "해당 47곳 중 A유형 19곳만, 나머지는 유지").
- **출력은 대화 본문에 인라인.** 파일로 빼지 않는다. 사용자는 읽고 바로 답하려고 이걸 요청했다.

## 승인 이후

승인이 오면 **결정된 것만** 실행한다. 보류된 작업은 손대지 않는다. 실행 중 보고서가 틀렸음이 드러나면 그 자리에서 밝히고 다시 묻는다 — 승인은 보고서 내용에 대한 것이지 백지 위임이 아니다.

## 하지 말 것

- 확인 안 한 것을 확인한 것처럼 쓰기
- 사용자 표현 대신 새 ID 부여
- 답할 수 있는 질문에 선택지 메뉴로 응답
- 승인 전 코드 편집
